# Phase 10 — 맵 에디터 세부 계획 (v1.1)

Phase 9에서 만든 것들 — docking ImGui, Inspector, 렌더러/ECS 경계 — 이
전부 이 단계의 재료다. 이 문서는 ROADMAP Phase 10 항목을 **커밋 단위로
쪼갠 실행 계획**이다. 계획 문서이므로 코드는 없고, 설계 결정과 검증
방법만 담는다.

---

## 1. 현재 상태 진단

Phase 9 종료(v1.0) 시점 코드의 한계. 각 항목이 세부 단계 하나와 대응된다.

| # | 문제 | 증상 | 해결 단계 |
|---|------|------|-----------|
| 1 | 씬이 스왑체인(백버퍼)에만 그려짐 | 에디터 창 "안에" 씬을 넣을 수 없음. 패널이 씬을 가림 | 10.1 |
| 2 | 종횡비가 스왑체인 크기에 묶임 | 뷰포트 창 크기 ≠ 창 크기가 되는 순간 화면이 찌그러짐 | 10.1 |
| 3 | 엔티티 생성·삭제가 코드에만 있음 | 런타임에 오브젝트를 놓거나 지울 수 없음 | 10.2 |
| 4 | Inspector가 편집만 가능 | Component 추가/삭제 불가 (ROADMAP 요구사항) | 10.2 |
| 5 | 엔티티에 이름이 없음 | 목록이 "Mesh #3" — 씬이 커지면 구분 불가 | 10.2 |
| 6 | 에셋 로드가 `BuildWorld` 하드코딩 | 새 모델 하나 보려면 재빌드 | 10.3 |
| 7 | 마우스가 UI만 조작 | 뷰포트 클릭으로 월드에 배치할 수 없음 | 10.4 |
| 8 | 씬 구성이 코드 = 휘발성 | 에디터로 만든 씬을 저장할 방법이 없음 | 10.5 |
| 9 | `kMaxObjects = 32` 고정 | 에디터로 배치하면 금방 초과 → 예외 | 10.2 |

**건드리지 않는 것** (이번 단계 범위 밖):
- Undo/Redo — 에디터의 정석이지만 커맨드 패턴 도입이 필요한 별개 주제. Phase 13 후보
- 이동/회전 기즈모(3D 핸들) — ImGuizmo 같은 서드파티 영역. Inspector 숫자 편집으로 충분히 시작
- 멀티 셀렉션, 프리팹 — 게임 로직이 생긴 뒤의 이야기
- 플레이 모드(에디터↔게임 전환) — 여기서도 범위 밖이지만 "언젠가"가 아니다.
  **ROADMAP Phase 12(플레이 모드 & 게임 런타임)** 로 승격됨 — 에디터는 개발
  도구이지 게임의 최종 실행 형태가 아니고, 10.5의 씬 포맷이 그 선행 조건이다
- 에셋 언로드 + 핸들 세대(generation) — 로드만 하는 동안은 불필요. 씬 전환으로 메모리가 아까워지는 순간이 트리거

## 2. 진행 원칙

Phase 9와 동일하다.

1. **한 단계 = 완결된 커밋 1~2개.** 각 단계가 끝날 때마다 빌드·실행·화면 확인.
2. **경계를 지킨다.** Renderer는 계속 ECS를 모른다. 에디터 UI(`Game/`)와
   렌더러 기능(`Graphics/`)이 섞이지 않는다 — 9.6의 ImGuiLayer/DebugUI 분리가 본보기.
3. **씬 데이터와 에디터 상태를 구분한다.** "무엇이 씬에 있나"는 컴포넌트,
   "지금 무엇을 선택했나"는 에디터 전용 상태. 저장 대상은 전자뿐.
4. 순서는 의존성 순이다: 뷰포트(10.1) 없이는 배치(10.4)가 무의미하고,
   배치 없이는 저장(10.5)할 씬이 코드 생성물뿐이다.

## 3. 단계 개요

| 단계 | 상태 | 주제 | 핵심 학습 | 규모(예상) | 태그 |
|------|------|------|-----------|-----------|------|
| 10.1 | 완료 | 오프스크린 렌더 타겟 + Scene Viewport | 렌더 투 텍스처, RT 수명 관리 | 대 | - |
| 10.2 | 완료 | 엔티티 편집 (생성·삭제·이름·컴포넌트) | 에디터 상태 vs 씬 데이터 | 중 | - |
| 10.3 | 완료 | 에셋 브라우저 | 디렉터리 스캔, 지연 로드 | 소 | - |
| 10.4 | 완료 | 뷰포트 배치 (픽킹) | 스크린→월드 언프로젝션, 레이-평면 교차 | 중 | - |
| 10.5 | 대기 | 씬 저장/불러오기 | 직렬화, 핸들을 어떻게 저장하나 | 중 | v1.1 |

**트리거 대기 항목은 전부 [ROADMAP](../ROADMAP.md) Phase 10 절에 등록한다.**
각 단계 결과에 산문으로 "나중에"라고 적는 것만으로는 목록이 되지 않는다 —
미룬 이유와 되살아날 조건이 한곳에 모여 있어야 판단이 가능하다.
현재: 멀티 머티리얼 Submesh, 씬 계층 구조, 메시 바운딩 박스(AABB),
비동기 에셋 로드, 메시 3D 썸네일, Object CB 동적화, RT 폐기 큐.
단계 번호를 주지 않는다 — 조건이 발생하면 그 시점의 단계에 끼워 넣는다.

## 4. 단계별 상세

### 10.1 오프스크린 렌더 타겟 + Scene Viewport

**목표**: 씬을 백버퍼가 아니라 우리가 만든 텍스처에 그리고, 그 텍스처를
`ImGui::Image`로 Scene Viewport 창 안에 표시한다. **Phase 11 그림자 매핑이
같은 기술(렌더 투 텍스처)을 쓰므로, 여기서 배우는 것이 그대로 이월된다.**

**작업 항목**
- [o] `RenderTarget` 클래스: 색상 텍스처(RTV+SRV 겸용) + 깊이 텍스처(DSV) + 크기
- [o] Renderer에 "화면에 그리기" 대신 "이 RT에 그리기" 경로 추가.
      백버퍼에는 ImGui만 그린다 (씬은 뷰포트 창 안에만 존재)
- [o] Scene Viewport 패널: `ImGui::Image(rt.SRV, 패널크기)`. 창 크기가 곧 해상도
- [o] 뷰포트 크기 변경 시 RT 재생성 (지연 처리 — 아래 함정 참조)
- [o] 종횡비를 스왑체인이 아니라 **RT 크기**에서 얻도록 투영 행렬 수정
- [o] 카메라 입력 게이트 변경: `WantCaptureMouse` 전역 차단 대신
      "뷰포트 창이 호버/포커스일 때만 카메라 조작"

**설계 결정**
- RT 포맷은 스왑체인과 동일(R8G8B8A8_UNORM). 포맷이 갈리면 PSO가 갈라진다
- 색상 텍스처 플래그: `ALLOW_RENDER_TARGET`, 상태 전이는
  `RENDER_TARGET ↔ PIXEL_SHADER_RESOURCE` — Phase 5 텍스처 업로드에서 배운
  배리어의 세 번째 용례
- RTV/DSV 슬롯은 9.3 할당자에서 받는다. RTV 힙이 SwapChain 소유(용량 2)라
  Renderer에도 RTV 할당자가 필요해짐 — 이 시점에 SwapChain 것과 통합할지
  별도로 둘지 결정 (권장: 별도. 수명이 다르다)

**함정**
- **GPU가 읽는 중인 RT를 재생성하면 안 된다.** 뷰포트 크기는 ImGui 프레임
  도중에 확정되는데, 그 프레임의 커맨드는 아직 옛 RT를 참조한다. 크기 변경은
  플래그만 세우고 **다음 프레임 시작(fence 확인 후)에** 재생성 — Window 리사이즈를
  지연 처리했던 것과 같은 패턴
- 뷰포트 크기가 0이 되는 순간(창 접힘)이 있다 — 0×0 RT 생성은 실패한다
- ImGui가 SRV를 `ImTextureID`로 받는다. 9.6에서 폰트가 쓰는 것과 같은
  셰이더 가시 힙 슬롯이어야 한다
- 씬을 백버퍼에 안 그리게 되면 **백버퍼 클리어 색이 곧 "에디터 배경"**이다.
  어두운 회색 정도로 바꿔야 도킹 빈 공간이 어색하지 않다

**완료 기준**: 씬이 도킹 가능한 Viewport 창 안에서 렌더링되고, 창을
늘리고 줄여도 찌그러지지 않으며(종횡비 = 창 비율), 다른 패널이 씬을
가리지 않는다.

**결과**

한 프레임이 두 패스로 갈라졌다.

| 패스 | 대상 | 깊이 | 배리어 |
|------|------|------|--------|
| 씬 | `RenderTarget` 색상 텍스처 | RT 소유 D32_FLOAT | `PIXEL_SHADER_RESOURCE ↔ RENDER_TARGET` |
| UI | 스왑체인 백버퍼 | 없음 | `PRESENT ↔ RENDER_TARGET` |

- 백버퍼의 깊이 버퍼가 **사라졌다**. UI만 받는 표면에는 필요 없다.
  `Renderer`가 들고 있던 `m_depthStencilBuffer`/`CreateSizeDependentResources`가
  통째로 `RenderTarget`으로 이사했고, `Renderer::Resize`는 스왑체인 한 줄만 남았다
- ImGui 백엔드에 넘기는 `DSVFormat`도 `UNKNOWN`으로 바꿨다. PSO가 선언한 포맷과
  실제 바인딩이 어긋나면 디버그 레이어 에러다
- RTV 할당자는 계획대로 SwapChain 것과 **분리**했다(용량 8). 수명이 다르다 —
  백버퍼 뷰는 창을 따라가고, 씬 RT 뷰는 패널을 따라간다. Phase 11 그림자 맵도
  여기서 슬롯을 받는다
- 디스크립터 **슬롯은 리사이즈에도 유지**하고 내용만 다시 쓴다. ImGui가 들고 있는
  `ImTextureID`가 그대로 유효해야 하기 때문 (SwapChain이 백버퍼 RTV에 쓰던 것과 같은 수법)

**검증**

1. **종횡비가 RT를 따르는가** — 폭 520 고정, 높이만 526 / 281로 바꿔 두 장을 찍었다.
   fovY가 고정이면 화면상의 모든 거리는 **높이에만** 비례하므로, 526짜리를 양축 0.534배로
   줄이면 281짜리와 겹쳐야 한다. 스왑체인 종횡비를 쓰는(=버그) 가설이면 가로는 안 줄어든다.

   | 가설 | 평균 절대 픽셀차 |
   |------|-----------------|
   | 양축 축소 (RT 종횡비) | **4.03** |
   | 세로만 축소 (스왑체인 종횡비) | 35.21 |

2. **카메라 입력 게이트** — 우클릭 드래그 후 뷰포트 픽셀 변화율.
   비교 기준은 "드래그 없이 같은 시간 대기"(애니메이션만)다.

   | 조작 | 뷰포트 변화 |
   |------|------------|
   | 커서 이동 없음 (기준선) | 15.99% |
   | Entities 패널 위에서 드래그 | 15.95% — 기준선과 동일, 카메라 안 움직임 |
   | 뷰포트 안에서 드래그 | 93.80% |

3. **리사이즈** — 패널 그립 드래그(520×526 → 853×594 → 406×307)와 OS 창 리사이즈를
   연속 수행. 크래시 없음, 종료 코드 0. 리사이즈 중 프레임 타임 그래프에 톱니가
   보이는데, 이것이 아래 "매 프레임 full flush" 비용이다
4. **디버그 레이어 메시지 0건**. `OutputDebugString`을 DBWIN 공유 버퍼로 가로채
   측정했고, 측정 장치 자체는 일부러 잘못된 `CreateCommittedResource`를 호출하는
   별도 프로그램으로 교정했다(그쪽은 에러가 정상 포착됨)

**구현하며 갈린 결정**

- 리사이즈 시 `WaitForFenceValue`가 아니라 **`WaitForGpu`(전체 플러시)** 를 쓴다.
  이 프레임의 fence만 기다리는 것으로는 부족하다 — 다른 프레임(N−1)이 아직 옛
  텍스처를 샘플링 중일 수 있다. 대가는 스플리터를 끄는 동안 매 프레임 플러시인데,
  드래그가 끝나면 즉시 사라진다. "제대로 하려면 프레임별 폐기 큐"는 트리거 대기
- 호버 판정은 **한 프레임 늦다.** 시스템이 UI보다 먼저 도는 순서를 유지했기 때문.
  UI를 먼저 돌리면 Inspector 편집을 같은 프레임의 시스템이 덮어쓴다 — 그쪽이 더 나쁘다
- 키보드 게이트는 `WantCaptureKeyboard`로 남겼다. 텍스트 입력 중이면 어디에 있든
  WASD를 삼켜야 하고, 마우스와 달리 "뷰포트 위"라는 개념이 없다

### 10.2 엔티티 편집 — 생성·삭제·이름·컴포넌트

**목표**: 씬을 코드 없이 편집하는 데 필요한 나머지 절반. 9.6 Inspector가
"값 편집"까지 했으니, 이제 "구조 편집"(엔티티/컴포넌트 단위 추가·삭제)을 더한다.

**작업 항목**
- [o] `Name` 컴포넌트 (문자열 하나). 목록 표시가 "Mesh #3" → "Crate_01"로
- [o] 엔티티 생성(빈 엔티티 + Transform 기본 장착) / 삭제 / 복제 버튼
- [o] Inspector에 "Add Component" — 컴포넌트 타입 목록에서 골라 장착
- [o] Inspector 각 섹션에 제거 버튼 (X)
- [o] `kMaxObjects` 상향 또는 동적화 — Object CB를 엔티티 수에 맞춰 재할당
      *(32 → 256 상향. 동적화는 트리거 대기)*
- [o] 삭제된 엔티티를 선택 중이었다면 선택 해제 (세대 검사가 이미 있으니
      `IsAlive` 확인만 추가 — 9.5에서 만든 generation이 여기서 첫 실전)

**설계 결정**
- Add Component 목록은 **수동 등록**으로 시작한다 (컴포넌트 7종을 나열하는
  switch 하나). 리플렉션/자동 등록은 타입이 수십 개일 때의 문제다
- 복제는 컴포넌트 단위 복사. Material 안의 핸들은 값 복사로 충분하다
  (핸들은 공유 참조라는 게 9.4 설계의 이득)

**함정**
- 엔티티 삭제는 **프레임 끝에 모아서**. ForEach 순회 도중 Destroy를 부르면
  swap-and-pop이 순회 중인 배열을 흔든다 — 삭제 큐에 넣고 순회 밖에서 처리
- Object CB 재할당은 GPU가 옛 버퍼를 읽는 중일 수 있다 — RT 재생성과 같은
  지연 패턴, 또는 "충분히 크게 한 번" (권장: 256으로 상향 후, 진짜 동적화는
  필요해질 때)

**완료 기준**: 마우스만으로 엔티티를 만들고, 이름 짓고, MeshRenderer를
붙여 화면에 등장시키고, 지울 수 있다.

**결과**

핵심은 **구조 편집을 큐에 넣는다**는 것 하나다.

값 편집(슬라이더)은 배열의 *모양*을 바꾸지 않으니 그 자리에서 써도 된다.
반면 Create는 순회 중인 dense 배열에 push_back 하고(재할당 = 반복자 무효화),
Destroy는 swap-and-pop으로 밑에서 원소를 빼낸다. 그래서 패널은 **명령을
쌓기만** 하고, 모든 패널이 순회를 끝낸 `DrawDebugUI` 마지막에 한 번
`ApplyCommands`가 실행한다.

- 컴포넌트 레지스트리는 **수동 테이블** — 타입당 한 줄:
  ```cpp
  const ComponentOps kComponents[] = { MakeOps<Name>("Name"), ... };
  static_assert(std::size(kComponents) == size_t(Comp::Count), ...);
  ```
  `MakeOps<T>`가 캡처 없는 람다 4개(has/add/remove/copy)를 함수 포인터로
  굽는다. 리플렉션 없이 "타입 목록을 순회"가 되고, 복제·Add Component 목록·
  섹션 제거가 전부 이 한 테이블을 쓴다
- `World::ForEachEntity` 추가. 컴포넌트 스토리지는 "누가 T를 갖고 있나"에만
  답하는데, 에디터 목록에 필요한 질문은 "무엇이 존재하나"다 —
  Transform으로 순회했다면 마지막 컴포넌트를 뗀 엔티티가 목록에서 사라져
  되돌릴 방법이 없어진다
- 섹션 제거 버튼은 손으로 만들지 않고 `CollapsingHeader(label, &keep, ...)`의
  내장 X를 쓴다
- `Add Component` 목록은 **이미 가진 타입을 뺀다**. 스토리지의 Add는 사실
  "덮어쓰기"라, 가진 걸 다시 고르면 값이 조용히 초기화된다
- 복제는 ActiveCamera만 건너뛴다. "정확히 하나"를 뜻하는 태그라 둘이 되면
  `FindActiveCamera`가 스토리지 순서에 따라 아무거나 고른다
- `kMaxObjects` 32 → 256. 프레임 세트당 64 KB라 아낄 대상이 아니다.
  진짜 동적화는 RT 재생성과 똑같은 지연 처리가 필요해서 트리거 대기

**검증** (좌표 지정 클릭 자동화 + 스크린샷 판독)

| 조작 | 결과 |
|------|------|
| 시작 | 19 entities, 15 drawn / 256. 목록이 Floor / Crate_00… / Camera / Sun 이름으로 표시 |
| Sphere 선택 → Duplicate | Entity #19 "Sphere copy", 20 entities **16 drawn**. Transform·Material·Spin 그대로 |
| New | Entity #20 "New Entity", Name+Transform만. 21 entities, **16 drawn**(그릴 게 없음) |
| Add Component 열기 | 이미 가진 4종이 빠지고 Camera / Light / Active Camera / Environment만 제시 |
| Light 추가 | 섹션이 생기고 **씬 조명이 즉시 바뀐다** — 런타임에 붙인 컴포넌트가 그대로 시스템에 참여한다는 증거 |
| 헤더 X | 컴포넌트가 사라지고 조명이 원래대로 |
| Sphere 선택 → Delete | 목록·씬에서 사라짐, 18 entities 14 drawn, Inspector "Nothing selected", 버튼 비활성 |

복제/생성/삭제를 9번 연속 수행 후에도 종료 코드 0, 디버그 레이어 메시지 0건.

**곁가지 정리**: `SpawnMesh(world, mesh, material, position, scale)`가
회전을 표현할 수 없던 문제(9.5에서 지적됨)를 여기서 해결했다. 두 인자
사이에 rotation을 끼워 넣으면 기존 호출의 scale 인자가 **조용히** 위치를
바꿔 읽힌다. 대신 `Transform` 하나를 받도록 **타입을 바꿔** 모든 호출부가
컴파일 에러가 되게 했다.

### 10.3 에셋 브라우저

**목표**: `Assets/` 폴더의 내용을 에디터에서 보고 고른다. 하드코딩된
`BuildWorld`가 "초기 씬"에서 "예시 씬 중 하나"로 강등되는 시작점.

**작업 항목**
- [o] `Assets/` 스캔: `.obj` → 메시 목록, `.png` → 텍스처 목록
- [o] Asset Browser 패널: 두 목록 표시, 클릭으로 "현재 선택 에셋" 지정
- [o] 선택 정보 표시 (파일 크기, 로드 여부. 메시면 로드 후 정점/삼각형 수)
- [o] 로드는 **선택 시점에** ResourceManager로 (지연 로드 — 시작할 때
      폴더 전체를 로드하지 않는다)
- [o] 미리보기: 텍스처는 SRV가 이미 있으니 `ImGui::Image`로 즉시 가능.
      메시 3D 썸네일은 **범위 밖** (RT가 또 필요한 일 — 트리거 대기)
- [o] *(계획 외)* Inspector에 "Assign mesh / Assign texture" — 브라우저에서
      고른 것을 선택 엔티티에 붙인다. 이게 없으면 로드된 메시를 눈으로
      확인할 방법이 없어 10.3을 검증할 수 없다

**설계 결정**
- 디렉터리 스캔은 `std::filesystem::directory_iterator`. 파일 감시(핫 리로드)는
  아직 안 한다 — 새로고침 버튼이면 충분
- ResourceManager는 수정 없이 그대로 쓴다. 브라우저는 "경로 목록을 보여주고
  선택되면 Load를 부르는" UI일 뿐 — 9.4 캐시 덕에 중복 선택이 공짜

**함정**
- OBJ 로드는 수십 ms가 걸릴 수 있다(laevat.obj는 Debug에서 6초였다).
  선택 즉시 로드하면 UI가 멈춘다 — 일단 수용하고 기록만. 비동기 로드는
  스레드가 필요한 별개 주제 (Phase 13 Job System의 트리거 후보)

**완료 기준**: Assets/에 파일을 넣고 새로고침하면 목록에 나타나고,
선택하면 정보가 표시된다. 재빌드 없이.

**결과**

`Game/AssetBrowser`는 계획대로 ResourceManager 바깥에 있다. 매니저는
로드된 에셋을 소유하고 디렉터리를 모르며, 브라우저는 파일 시스템을 걷고
**선택된 순간에만** Load를 부른다. 9.4 캐시 덕에 같은 걸 두 번 골라도 공짜다.

- 목록은 즉시, 로드는 클릭 시. 이름 옆 `*`가 "이미 GPU에 있음" 표시라
  클릭 비용을 누르기 전에 알 수 있다
- 텍스처 미리보기는 렌더러가 샘플링하는 **바로 그 SRV**를 `ImGui::Image`에
  넘긴 것이다. 메시 3D 썸네일은 에셋마다 RT가 필요해서 계획대로 범위 밖
- 파일 경로는 wide, ImGui는 UTF-8 — 변환은 `AssetBrowser.cpp` 한 곳에만 있다
- 로드 실패는 잡아서 "failed to load"로 표시한다. 깨진 파일 하나가 에디터를
  같이 데려가면 안 된다

**계획을 벗어난 세 가지** (모두 이 단계가 드러낸 문제다)

1. **기본 텍스처 (`#white` 1×1)**. 에디터에서 붙인 MeshRenderer는 텍스처가
   없는데, `TextureSRV(invalid)`는 예외를 던진다. 지금까지는 모든 머티리얼이
   텍스처를 갖고 있어서 닿지 않던 경로다. 흰 텍셀은 albedo에 1을 곱하므로
   머티리얼 색이 그대로 나온다. `AddTexture(name, ImageData)`를 갈라내
   `LoadTexture`가 그걸 쓰게 했다 — `AddMesh`/`LoadMesh`와 같은 모양
2. **`BuildWorld`의 `L"Laevat.obj"` → `L"laevat.obj"`**. 디스크의 파일은
   소문자다. 윈도우는 둘 다 열어주지만 **캐시는 문자열로 키를 잡는다** —
   브라우저가 `laevat.obj`를 요청하는 순간 23 MB짜리 지오메트리가 두 번째
   GPU 버퍼로 다시 올라갔을 것이다. **이건 호출부 하나를 고친 것이지
   정책이 아니다** — 정규화 정책은 10.5 "경로 정규화"에 작업 항목과 결정할
   목록으로 적어뒀다. 씬 파일이 경로를 저장하기 시작하면 철자를 통제할 수
   없어져서 더는 미룰 수 없다
3. **`ResourceManager::FindMesh/FindTexture`** (읽기 전용 캐시 조회).
   시작 씬이 로드해둔 에셋을 브라우저가 "미로드"로 표시하면 거짓말이 된다
4. **"drawn" 카운터 수정**. `MeshRenderer`를 가진 엔티티 수를 세고 있었는데,
   메시가 안 붙은 것은 렌더러가 건너뛴다. 이제 렌더러가 실제로 받은
   DrawItem 개수를 표시한다 — 그림과 어긋나는 계기판은 없느니만 못하다

**검증**

| 조작 | 결과 |
|------|------|
| 시작 | Assets 패널에 `3 obj, 2 png`. 시작 씬이 로드한 5개 전부 `*` 표시 |
| Sphere.obj 선택 | 70.4 KB, already loaded, **561 vertices, 1024 triangles** |
| laevat.obj 선택 | 23.2 MB, already loaded, **216912 vertices, 72304 triangles** (정점/삼각형 = 3.0 — 이 모델은 코너마다 v/vt/vn 조합이 달라 중복 제거가 전혀 안 된다) |
| Crate.png 선택 | 5.4 KB, 미리보기 이미지가 패널에 렌더링 |
| **재빌드 없이**: Assets/에 23 MB obj 복사 → Refresh | `4 obj, 2 png`, 목록에 등장, `*` 없음 |
| 그것을 클릭 | **loaded in 5043.0 ms** — 그동안 UI가 완전히 멈춘다 |
| New → Add Component(Mesh Renderer) | 20 entities, **15 drawn** (메시가 없으니 그려지지 않는다), Assign 버튼 둘 다 비활성 |
| Sphere.obj 선택 → Assign mesh | handle 3, **16 drawn**. 텍스처는 아직 없어 흰 기본 텍스처로 그려진다 (예전이라면 여기서 예외) |
| Crate.png 선택 → Assign texture | 텍스처가 입혀진다 |

디버그 레이어 메시지 0건, Debug/Release 모두 종료 코드 0.

**5초 멈춤에 대해**: 계획대로 수용하고 기록만 한다. 비동기 로드는 스레드가
필요한 별개 주제이고, 트리거는 "에셋을 고르는 게 실제로 괴로워지는 순간"이다.
참고로 이 측정 자체가 함정이었다 — 클릭 직후 0.5초에 화면을 찍으면 로드가
UI 스레드를 붙잡고 있어 **직전 프레임이 그대로 남아 있다**. 캡처를 20초로
늘리고서야 숫자가 보였다.

### 10.4 뷰포트 배치 (픽킹)

**목표**: 브라우저에서 고른 에셋을 뷰포트 클릭 지점의 바닥 위에 놓는다.
스크린 좌표 → 월드 레이 변환은 이후 모든 마우스 상호작용(선택, 기즈모)의 기초다.

**작업 항목**
- [o] 뷰포트 내부 마우스 좌표 계산 (ImGui 창 위치·패딩 보정 → 0~1 정규화)
- [o] 언프로젝션: NDC → 뷰 공간 → 월드 공간 레이 (투영·뷰 행렬의 역)
- [o] 레이-평면 교차: 바닥(y=0)과의 교점 = 배치 위치
- [o] 배치 모드: 에셋 선택 상태에서 뷰포트 클릭 → 그 자리에 Entity 생성
      (Name + Transform + MeshRenderer, 텍스처는 브라우저에서 선택된 것)
- [] 클릭 픽킹(이미 있는 엔티티 선택)은 **바운딩 없는 지금은 보류** —
      레이-AABB 교차는 바운딩 박스 도입과 함께 (트리거: 뷰포트에서 직접
      선택하고 싶어지는 순간, 사실상 곧)

**설계 결정**
- 언프로젝션은 `XMMatrixInverse(view * proj)` 한 번이면 된다. DirectXMath의
  `XMVector3Unproject`를 써도 되지만, 행렬을 직접 뒤집어 보는 쪽이 학습 목적에
  맞다 — 뷰 행렬이 "카메라 변환의 역"이라던 Phase 6 개념의 복습
- 배치 높이는 바닥 고정(y=0 평면). 메시 바운딩을 모르니 절반 파묻힐 수
  있다 — 바운딩 박스(위 픽킹과 같은 트리거)가 생기면 바닥 위에 정확히 얹는다

**함정**
- 마우스 좌표는 **스왑체인이 아니라 뷰포트 RT 기준**으로 정규화해야 한다.
  10.1에서 종횡비를 RT로 옮긴 것과 같은 이유 — 이걸 놓치면 클릭 지점과
  배치 지점이 어긋나고, 창을 리사이즈할수록 더 어긋난다
- ImGui 창 안이라 `WantCaptureMouse`가 항상 true다 — "뷰포트 이미지 위"인지는
  `ImGui::IsItemHovered()`로 따로 판단해야 한다

**완료 기준**: 브라우저에서 메시를 고르고 뷰포트의 바닥을 클릭하면 그
지점에 엔티티가 생긴다. 창 크기를 바꿔도 클릭 지점이 정확하다.

**결과**

`Game/Picking`은 렌더링의 정확한 역방향이다. 정점 셰이더가 월드 좌표를
view·proj로 픽셀까지 밀어내는 것을, 여기서는 픽셀을 레이로 되돌린다.

```cpp
invViewProj = XMMatrixInverse(nullptr, view * proj);
near = XMVector3TransformCoord({ndcX, ndcY, 0, 1}, invViewProj);
far  = XMVector3TransformCoord({ndcX, ndcY, 1, 1}, invViewProj);
```

- **곱한 뒤 한 번 뒤집는다.** proj와 view를 따로 뒤집을 이유가 없고,
  틀릴 곳이 두 군데가 아니라 한 군데가 된다
- `z = 0`이 근평면, `1`이 원평면 — **D3D의 깊이 범위**다. OpenGL의 -1을
  그대로 옮기는 것이 전형적인 포팅 버그고, 레이가 카메라 뒤에서 시작하는데도
  그림은 거의 맞아 보여서 발견이 늦다
- `TransformCoord`여야 한다. `w`로 나누는 원근 분할이 여기 들어 있고,
  빼면 위치가 아닌 동차 좌표가 남는다
- 레이 방향은 **정규화하지 않는다**. "근평면→원평면"이고, 평면 교차는
  비율이라 길이가 약분된다

**경계에 관한 결정 하나**: `GetActiveCameraView`를 `BuildRenderData`에서
떼어냈다. 픽킹은 **렌더러가 실제로 그린 그 카메라**로 언프로젝션해야 하는데,
카메라를 따로 재구성하면 클릭이 가리키지 않은 곳에 떨어지는 종류의 버그가
생긴다. 종횡비도 같은 이유로 `Renderer::SceneAspectRatio()`(=RT의 종횡비)를
쓴다 — 창의 것을 쓰면 두 값의 비율만큼 가로로 빗나간다.

**그리고 그 함수는 출력을 전부 채워야 한다.** 처음에는 `CameraComponent`가
없을 때 fovY/near/far를 건드리지 않았는데, 두 호출자가 구조체를 **다르게
초기화한다** — 렌더러는 프레임을 넘어 재사용하는 하나를 넘기고, 픽킹은
매번 새로 만든 것을 넘긴다. 그래서 FOV를 편집한 뒤 Camera 컴포넌트를 떼면
렌더러는 편집값을, 픽킹은 기본 45°를 쓰는 상태가 되고 클릭이 어긋난다.
재현: FOV를 150°로 올리고 컴포넌트를 제거해도 **화면이 150° 그대로였다.**
렌즈가 없으면 기본 컴포넌트를 대입하도록 고쳐서, 성공 시 여섯 필드가 모두
덮어써진다. "호출자가 넘긴 값이 답에 섞이지 않는다"가 규칙이다.

배치는 10.2의 명령 큐에 `Place`로 얹었다. 클릭은 패널을 그리는 도중에
발생하므로, 다른 구조 편집과 똑같이 프레임 끝에 적용된다.

배치 모드는 Assets 패널의 **"Place on click" 체크박스**로 명시적으로 켠다.
"메시가 선택돼 있으면 항상 배치"가 더 짧지만, 그러면 뷰포트를 다른 용도로
클릭할 수 없어진다 — 그리고 기존 엔티티 클릭 선택이 바로 그 자리에 들어온다.

**검증** — 눈으로 보는 대신 **해석적으로 계산한 좌표와 대조**했다.

카메라는 (0, 3.5, -22), forward +Z, fovY 45°. 뷰 공간 방향은
`(ndcX·aspect·tan(fov/2), ndcY·tan(fov/2), 1)`이고 회전이 항등이라
월드 방향과 같다. `t = -3.5 / dir.y`, 교점 `= eye + t·dir`.

| 클릭 | 뷰포트 | ndc | 예측 | Inspector 실측 |
|------|--------|-----|------|----------------|
| A | 460×361 | (0, −0.5014) | x=0.000, z=−5.147 | **0.000, −5.148** |
| B | 460×361 | (−0.5, −0.5014) | x=−4.448, z=−5.147 | **−4.448, −5.148** |
| C | 660×361 | (−0.5, −0.5014) | x=−6.381, z=−5.147 | **−6.381, −5.147** |

B와 C는 **ndc가 같고 종횡비만 다르다.** z는 그대로고 x만 종횡비에 비례해
움직이는 것이 종횡비를 올바른 쪽에서 가져왔다는 증거다. 만약 스왑체인
종횡비(1280/720)를 썼다면 B는 −6.205가 나왔어야 한다 — 실측 −4.448과
명확히 구분된다.

- 하늘 클릭(ndcY = +0.72): 엔티티 수 변화 없음, 선택도 그대로. `t < 0` 가드
- 연속 3회 배치: 22 entities / 18 drawn, 텍스처까지 적용됨
- 디버그 레이어 메시지 0건, Debug/Release 종료 코드 0

**남긴 것** — ROADMAP 트리거 대기 항목 **메시 바운딩 박스(AABB)** 로 등록:
배치된 메시는 원점이 중심이라 **바닥에 반쯤 파묻히고**, 기존 엔티티를
클릭으로 고를 수도 없다. 둘 다 정점 범위 하나만 있으면 풀리는 문제라
한 항목으로 묶었다. 트리거는 "뷰포트에서 직접 선택하고 싶어지는 순간".

### 10.5 씬 저장 / 불러오기

**목표**: 에디터로 만든 씬이 프로그램 종료를 살아남는다. v1.1 마감.

**작업 항목**
- [ ] 씬 파일 포맷 설계 (아래 결정 참조) — `Assets/Scenes/*.scene`
- [ ] 저장: World를 순회하며 엔티티별 컴포넌트 직렬화
- [ ] 불러오기: 파일 파싱 → World 재구성. **핸들이 아니라 경로를 저장**한다는
      게 핵심 — MeshHandle 3번은 다음 실행에서 아무 의미가 없다.
      저장은 `"Sphere.obj"`, 로드는 ResourceManager가 경로 → 새 핸들
- [ ] 절차적 메시(#cube 등)는 이름 그대로 저장하고, 로드 시 이름을 보고
      `AddMesh(Make...)`로 재생성
- [ ] **경로 정규화 정책 결정** (10.3이 남긴 숙제 — 아래 설계 결정 참조)
- [ ] File 메뉴: New / Open / Save / Save As (ImGui 메인 메뉴바)
- [ ] `BuildWorld`를 "기본 씬 생성"으로 유지하되, 시작 시 마지막 씬을
      열지는 선택 사항

**설계 결정**
- **자체 텍스트 포맷 (권장)**, JSON 라이브러리 벤더링 대신. 이유:
  씬 구조가 단순하고(엔티티 목록 × 고정 컴포넌트 7종), 직렬화를 손으로
  한 번 써봐야 "버전 필드는 왜 필요한가, 부동소수점은 어떻게 저장하나" 같은
  문제를 직접 만난다. 사람이 읽고 diff할 수 있는 줄 단위 포맷:
  ```
  scene 1            # 버전
  entity "Crate_01"
    transform 3.0 1.0 -4.0  0 0 0  1 1 1
    meshrenderer mesh="Crate.obj" texture="Crate.png" shininess=64 ...
  ```
  글자 그대로가 아니라 방향 제시다. 구현 시 확정한다
- 첫 줄에 **버전 번호**. 포맷이 바뀌는 순간(반드시 온다) 옛 파일을 구분할
  유일한 수단
- float은 `%.9g`로 저장 — 왕복(저장→로드) 시 비트 손실 없는 최소 자릿수
- 에디터 상태(선택, 카메라 위치)는 저장하지 않는다… 카메라는 예외로
  저장하면 편하다 — 씬 데이터가 아니라 별도 섹션으로

- **경로 정규화** — 10.3에서 미룬 결정을 여기서 갚는다.

  `ResourceManager`의 캐시는 요청 문자열을 그대로 키로 쓴다. 윈도우 파일
  시스템은 대소문자를 구분하지 않으므로 `Laevat.obj`와 `laevat.obj`는 같은
  파일을 열면서 **서로 다른 캐시 항목**이 된다 — 같은 지오메트리가 GPU에
  두 벌 올라간다. 10.3에서는 `BuildWorld`의 철자를 디스크와 맞추는 것으로
  덮어뒀지만, 그건 호출부 하나를 고친 것이지 정책이 아니다.

  씬 파일이 경로를 저장하기 시작하면 이걸 더는 미룰 수 없다. 사람이 손으로
  편집하거나 다른 기계에서 만든 씬 파일이 어떤 철자로 들어올지 통제할 수
  없기 때문이다. 결정해야 할 것:

  1. **정규화 위치** — `ResourceManager`가 키를 만들 때 한 번(권장). 호출부
     전부가 규칙을 기억해야 하는 방식은 반드시 새는 곳이 생긴다
  2. **정규화 규칙** — 소문자화 + 구분자를 `/`로 통일이 최소선. 대소문자를
     구분하는 파일 시스템으로 옮기면 소문자화가 **틀린 답**이 되므로,
     "윈도우 전용 가정"임을 코드에 명시할 것
  3. **저장 형식** — 절대 경로는 다른 기계에서 무의미하다. `Assets/` 기준
     상대 경로로 저장하고, 로드 시 `GetAssetDir()`에 이어 붙인다
  4. 절차적 메시 키(`#cube`)는 파일이 아니므로 정규화 대상이 아니다 —
     `#` 접두어가 이미 그 구분을 하고 있다

**함정**
- 파싱 실패 처리: 깨진 파일을 열다 절반만 로드되면 World가 오염된다 —
  **임시 World에 로드 후 성공하면 교체**, 실패하면 기존 씬 유지 + 에러 표시
- 한글 파일명/경로 — 파일 IO는 `std::filesystem::path`(wchar) 경유 유지.
  포맷 내부 문자열은 UTF-8로 통일
- 소문자화를 고른다면 `std::tolower`를 **char에** 쓰면 안 된다. UTF-8
  멀티바이트 시퀀스를 바이트 단위로 뭉갠다 — 정규화는 wide 문자열 상태에서
  하고, UTF-8 변환은 그 뒤에
- 저장 순서: unordered_map 순회는 실행마다 순서가 다르다 → 같은 씬을 두 번
  저장하면 diff가 난다. 엔티티 인덱스 순으로 정렬해서 저장

**완료 기준**: ROADMAP 완료 기준 그대로 — 배치·편집한 씬을 저장하고,
프로그램을 재시작해 불러왔을 때 동일하게 복원된다. **여기서 `v1.1` 태그.**
